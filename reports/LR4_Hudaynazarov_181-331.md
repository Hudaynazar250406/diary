## Архитектура контейнерного окружения

```text
                хост
                  |
               :8080 (единственный опубликованный порт, сеть frontend)
                  |
        [ nginx:1.27-alpine ]      <- балансировщик, retry на другой экземпляр
            |           |
   [ web x2 (gunicorn, USER app) ] <- replicas: 2, порты наружу не открыты
                  |
      [ postgres:16-alpine ]       <- порт БД не публикуется, данные в volume
                  |
       сеть backend (internal, без доступа наружу)
```

| Сервис | Образ | Порт | Лимиты ресурсов |
|---|---|---|---|
| nginx | `nginx:1.27-alpine` | `8080:80` (опубликован) | 0.25 CPU / 64M |
| web ×2 | `studenttrack-web:1.0.0` (сборка из Dockerfile) | 5000 (только внутри сети) | 0.50 CPU / 256M |
| db | `postgres:16-alpine` | 5432 (только внутри сети) | 1.0 CPU / 512M |

## Основное задание

### 1. Dockerfile приложения и .dockerignore

**Выполнено.** `Dockerfile` на базе `python:3.13-slim`: установка зависимостей из
запинованного `requirements.txt`, создание системного пользователя `app`,
копирование кода с правами `app:app`, запуск через gunicorn (2 воркера,
логи в stdout). `.dockerignore` исключает из образа `.git`, `.env`, виртуальные
окружения, кэши, тесты, бэкапы и каталог `nginx/` — в образ попадает только
необходимое для работы приложения.

### 2. Воспроизводимая сборка образа

**Выполнено.** Все версии зафиксированы: базовый образ `python:3.13-slim`,
зависимости в `requirements.txt` с точными версиями (`Flask==3.0.3`,
`psycopg[binary]==3.3.6`, ...), gunicorn запинован отдельно (`gunicorn==23.0.0`),
образы сервисов `postgres:16-alpine`, `nginx:1.27-alpine`, собираемый образ
получает фиксированный тег `studenttrack-web:1.0.0`. Тег `latest` нигде не
используется — проверяется автоматически (см. п. 12).

```bash
docker compose build
# Image studenttrack-web:1.0.0 Built
```

### 3. Запуск от непривилегированного пользователя

**Выполнено.** В Dockerfile создан пользователь `app` (uid 1000), контейнер
запускается от него (`USER app`). Проверено внутри контейнера:

```bash
docker compose exec -T --index 1 web whoami
# app
```

### 4. Настройки через переменные окружения

**Выполнено.** Все настройки передаются через переменные окружения:
`DATABASE_URL`, `SECRET_KEY`, `APP_PORT`, `FLASK_ENV` (web),
`POSTGRES_USER/PASSWORD/DB` (db). Значения подставляются в `docker-compose.yml`
из файла `.env` (не коммитится, исключён из образа через `.dockerignore`).
Шаблон — `.env.example`. Секреты в образ не помещаются.

### 5. Корректное завершение по сигналу остановки

**Выполнено.** Docker при остановке посылает SIGTERM; gunicorn как PID 1
обрабатывает его корректно: мастер-процесс прекращает приём новых соединений
и дожидается завершения текущих запросов воркерами. В compose задан
`stop_grace_period: 30s`. Проверено — контейнер завершается штатно с кодом 0:

```bash
docker stop <web-контейнер>
docker inspect -f '{{.State.ExitCode}}' <web-контейнер>
# 0
```

### 6. Compose-конфигурация для приложения и базы данных

**Выполнено.** `docker-compose.yml` описывает три сервиса: `db` (PostgreSQL 16),
`web` (приложение, 2 экземпляра), `nginx` (точка входа). Для локальной
разработки без полного контура добавлен оверрейд `docker-compose.dev.yml`,
публикующий порт БД на хост (`make dev-db`).

### 7. Внутренняя сеть, volume, healthcheck и порядок запуска

**Выполнено.**

- Сети: `backend` (`internal: true` — без доступа контейнеров наружу) для
  db/web/nginx и `frontend` для опубликованного порта nginx.
  *Замечание:* контейнер, подключённый только к `internal`-сети, недоступен
  через опубликованный порт на Docker Desktop для Windows (проверено
  экспериментально), поэтому nginx подключён к обеим сетям.
- Volume: `studenttrack_pgdata` для данных PostgreSQL.
- Healthcheck у каждого сервиса: `pg_isready` (db), HTTP GET `/health` (web),
  `wget /health` (nginx).
- Порядок запуска: `web` ждёт `db` (`condition: service_healthy`),
  `nginx` ждёт оба экземпляра `web`.

```bash
docker compose ps
# studenttrack_postgres   Up (healthy)   5432/tcp
# studenttrack-web-1      Up (healthy)   5000/tcp
# studenttrack-web-2      Up (healthy)   5000/tcp
# studenttrack_nginx      Up (healthy)   80/tcp
```

### 8. Порт БД не публикуется

**Выполнено.** В основном compose у `db` нет `ports:` (только `expose` внутри
сети). С хоста порт 5432 недоступен — проверяется автоматической проверкой
конфигурации (`make container-check`, проверка «порт БД не публикуется»).

### 9. Сохранение данных после пересоздания контейнеров и обновления образа

**Выполнено, проверено.** Создана контрольная запись, контейнеры пересозданы,
затем образ пересобран и контейнеры обновлены — данные сохранились:

```bash
docker compose exec -T db psql -U studenttrack -d studenttrack \
  -c "INSERT INTO groups (group_name, year, curator) VALUES ('PERSIST-TEST', 2099, 'Persistence Check');"

docker compose down && docker compose up -d
docker compose exec -T db psql -U studenttrack -d studenttrack -c "SELECT group_name FROM groups;"
# PERSIST-TEST — данные на месте после пересоздания

docker compose build && docker compose up -d
# PERSIST-TEST — данные на месте после обновления образа
```

### 10. Миграции, резервное копирование и восстановление в контейнерной среде

**Выполнено, проверено.**

Миграции применяются внутри контейнера:

```bash
make migrate
# docker compose exec -T --index 1 web python -m flask --app run db upgrade
# Running upgrade -> 800d075a19ea, baseline schema
# Running upgrade ... -> 42120a585a8f, add group curator
```

Резервное копирование:

```bash
make backup
# Backup -> backups/backup_20261009_125751.sql
# OK: backup_20261009_125751.sql (15378 bytes)
```

Восстановление **в новый volume** (полный сценарий потери и возврата данных):

```bash
docker compose down -v        # контейнеры и volume удалены
docker compose up -d          # чистое окружение: \dt → таблиц нет
make restore                  # scripts/restore.py — сброс схемы + загрузка дампа
# OK: restored
docker compose exec -T db psql -U studenttrack -d studenttrack -c "SELECT group_name FROM groups;"
# PERSIST-TEST — данные восстановлены из дампа
```

### 12. Автоматическая команда make container-check

**Выполнено.** `make container-check` запускает `scripts/container_check.py` —
24 автоматические проверки в пяти группах:

1. **Статическая конфигурация** (`docker compose config --format json` + Dockerfile):
   нет тегов `latest`, образы запинованы, healthcheck у каждого сервиса, порт БД
   и порт приложения не публикуются, опубликован только порт nginx, сеть
   `backend` — internal, реплик web ≥ 2, в Dockerfile `USER app` (не root).
2. **Сборка и запуск** окружения, ожидание `healthy` у всех контейнеров.
3. **Доступность и балансировка**: `/health` через nginx, минимум два разных
   идентификатора `instance` в ответах.
4. **Пользователь процесса**: `whoami` в контейнере web ≠ root.
5. **Отказоустойчивость**: остановка одного экземпляра web, доступность сервиса,
   код выхода остановленного контейнера = 0, восстановление экземпляра.

Фактический прогон:

```text

4. Пользователь процесса           — whoami -> app
5. Отказоустойчивость              — код выхода 0, сервис доступен, экземпляр восстановлен
```

## Дополнительное задание: Nginx, масштабирование и отказоустойчивость

### 1. Nginx как отдельный контейнер

**Выполнено.** Сервис `nginx` на образе `nginx:1.27-alpine`, конфигурация
примонтирована read-only из `nginx/nginx.conf`.

### 2. Запрет прямого доступа к приложению

**Выполнено.** Порт приложения (5000) не публикуется на хост — `expose` только
внутри сети `backend`. Проверено: `curl http://127.0.0.1:5000/` с хоста —
connection refused; автопроверка подтверждает отсутствие `ports` у web.

### 3. Не менее двух экземпляров приложения

**Выполнено.** `deploy.replicas: 2` для сервиса web — запущены контейнеры
`studenttrack-web-1` и `studenttrack-web-2`.

### 4. Распределение запросов между экземплярами

**Выполнено.** Встроенный DNS Docker (`127.0.0.11`) возвращает для имени `web`
адреса обеих реплик; nginx перечитывает список каждые 5 секунд
(`resolver 127.0.0.11 valid=5s`, имя upstream через переменную — иначе nginx
запомнил бы адреса только на старте).

### 5. Идентификатор экземпляра в ответе

**Выполнено.** `/health` возвращает поле `instance` — hostname контейнера:

```bash
for i in $(seq 1 6); do curl -s http://127.0.0.1:8080/health; echo; done
# {"instance":"e77a2af6b944","status":"ok"}
# {"instance":"9bb43d52ff9c","status":"ok"}
# {"instance":"e77a2af6b944","status":"ok"}
# {"instance":"9bb43d52ff9c","status":"ok"}
# ...
```

Запросы чередуются между двумя экземплярами — балансировка работает.

### 6. Остановка одного экземпляра — сервис доступен

**Выполнено, проверено автоматически** (проверка №5 в `make container-check`):
один контейнер web останавливается (`docker stop`), сервис продолжает отвечать
через nginx (первый же запрос успешен), затем экземпляр восстанавливается.

### 7. Исключение неработающего узла / повтор запроса

**Выполнено.** В nginx настроен повтор неудачного запроса на другой экземпляр:

```nginx
proxy_next_upstream error timeout http_502 http_503;
proxy_next_upstream_tries 3;
proxy_next_upstream_timeout 10s;
```

Повторяются только идемпотентные методы (GET, PUT, DELETE и т. д.) —
POST-запросы не дублируются, чтобы не создавать дубли записей. Обновление
списка живых узлов — через DNS (`valid=5s`).

### 8. Что мешает горизонтальному масштабированию

Проанализировано и описано в README:

- **PostgreSQL — единственный компонент с состоянием.** Реплики web читают
  и пишут в один primary; масштабирование самой БД потребовало бы внешнего
  решения (managed PostgreSQL, Patroni). До этого предела web-реплики
  масштабируются свободно.
- **Миграции БД должны выполняться один раз** (`make migrate`), а не при старте
  каждой реплики — иначе возможна гонка конкурирующих миграций.
- **Сессии — клиентские подписанные cookie Flask**, состояние на сервере не
  хранится: реплики взаимозаменяемы, sticky-сессии не нужны. Требование —
  одинаковый `SECRET_KEY` у всех экземпляров (задаётся через `.env`).
- Общих файлов (загрузок) у приложения нет; при их появлении потребуется общее
  хранилище (общий volume или объектное хранилище).
- Ограничение nginx open source: нет активных проверок upstream, список реплик
  обновляется по DNS, а не мгновенно — частично компенсируется
  `proxy_next_upstream` и малым `valid`.
