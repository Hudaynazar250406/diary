# Правила внесения изменений

Этот документ описывает обязательный процесс работы с репозиторием.
Нарушение правил — основание для отклонения изменений.

## Процесс изменения

1. **Задача.** Любое изменение начинается с задачи (issue).
2. **Ветка.** Создаётся от `main`:
   - `feature/<короткое-имя>` — новая функциональность
   - `fix/<короткое-имя>` — исправление бага
   - `docs/<короткое-имя>` — документация
   - `chore/<короткое-имя>` — рутина (зависимости, конфиги)
3. **Коммиты.** Осмысленные сообщения: `feat:`, `fix:`, `docs:`, `chore:`. Один коммит — одно логическое изменение.
4. **Локальная проверка.** Перед PR обязательно `make verify`.
5. **Pull Request.** PR создаётся в `main`. В описании: что сделано, зачем, как проверить.
6. **Ревью.** Минимум один участник команды одобряет PR.
7. **Merge.** После одобрения и прохождения CI — squash-merge в `main`.
8. **Удаление ветки.** После merge ветка удаляется.

## Обязательные проверки перед merge

- `pytest -q` — все тесты проходят
- `flake8` — без ошибок
- `make verify` — полный контур локальных проверок
- CI — зелёный (когда настроим)
- Код читается и объясняется автором

## Запрещено

- Прямой push в `main` (только через PR)
- Коммит секретов (`.env`, ключи, пароли, токены)
- Удаление или отключение тестов
- Снижение порогов качества (coverage, flake8)
- Отключение CI или его проверок
- Merge без ревью
- `git push --force` на общих ветках
- Изменение критических файлов (`Makefile`, `.flake8`, `pytest.ini`, `requirements.txt`) без явного обсуждения в PR

## Приёмка

- Релиз помечается тегом `vX.Y.Z`.
- Перед приёмкой — живая демонстрация работы приложения.
- На приёмке может быть контрольное изменение.
- Секреты и локальные файлы не должны попадать в репозиторий.

## Критические файлы

Изменения в этих файлах требуют отдельного ревью:

- `Makefile`
- `requirements.txt`
- `.flake8`, `setup.cfg`, `pytest.ini`
- `.github/workflows/*`
- `Dockerfile`, `docker-compose.yml`
- `tests/conftest.py`
- `.gitignore`
